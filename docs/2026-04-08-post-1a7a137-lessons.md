# 1a7a137 之后实验教训总结

## 目的

本文档记录 `1a7a1379e857131a7634bbfea480cf1f5ac4ba9b` 之后整段实验线的结论、失败模式和后续约束。

结论先写在最前面：

- 对主线默认模型而言，`1a7a137` 之后的结构改动整体上没有保留价值。
- 后续提交最多只保留了局部消融信息或工程脚手架价值，不应继续作为默认模型演化基础。
- 新开发从 `1a7a137` 重新开始是正确选择。

## 基线事实

`1a7a137` 是当前确认过的效果基线。

### 基线数值

| 数据集 | 基线最好结果 | 说明 |
| --- | --- | --- |
| assist_09 | `0.795446` | `best_no_E` |
| assist_09 full | `0.795256` | `e_rescue_full` |
| junyi | `0.828260` | `best_no_E` |
| junyi full | `0.827933` | `e_rescue_full` |

这意味着后续所有实验至少要回答两个问题：

1. 有没有稳定超过这个基线？
2. 就算没有超过，是否至少在一个明确目标上给出足够强的证据，值得保留进主线？

`1a7a137` 之后的大多数实验都没有同时满足这两个条件。

- 主线必须服从指标，而不是服从模型叙事。

## 这段历史最核心的失败模式

### 1. 主线目标漂移

后续很多工作在事实上已经不再是“稳定超过基线”，而是在追求：

- 更完整的结构故事
- 更丰富的模块命名
- 更复杂的 residual / routing / decouple 设计
- 更方便自动化的大规模实验编排

这些都不是主线目标。

主线目标只有一个：稳定超过基线，且回归风险可控。

### 2. 没有及时承认错误方向

从 E rescue 到 routing 再到 HyperLens/XB，很多信号其实已经很明确：

- `assist_09` 没有回到基线
- `no_E` 或更简化 ablation 更稳
- full 经常不如简化版本

但是主线没有及时停下来，而是沿着同一方向继续堆复杂度。

### 3. 过早把“局部有效”误判成“主线可用”

`junyi` 局部提升、某个 seed 高点、某个组件单独有信号，都被过早解释为“这条线还有希望”。

正确理解应该是：

- 局部有效，只说明它可以继续当假设
- 只有跨数据集或至少目标数据集稳定有效，才可以进入主线

### 4. 结果记录方式污染了判断

后半段 `results/experiment_results.csv` 带有追加、重复和历史残留。

这会导致两个问题：

- 很容易误把旧结果当成新结果
- 很容易把某次临时实验的高点错当成当前版本真实能力

正确做法应该是每次实验只看它自己的 `summary_mean.csv` 和 `diagnosis.csv`。

### 5. 主线和实验平台混在一起

自动化、runner、policy、实验编排这些工程资产，和模型结构实验被混在同一个主线里推进。

结果是：

- git 历史里“模型改动”和“平台改动”纠缠
- 回退时很难只回退模型，不伤到工程脚手架
- 讨论模型优劣时容易被无关提交干扰

## 从现在开始必须遵守的规则

### 规则 1：主线只承认基线门槛

默认门槛如下：

- `assist_09` 不能低于 `0.795446`
- `junyi` 不能低于 `0.828260`

如果一个新 full 模型达不到这个门槛，它就不是主线候选。

### 规则 2：一个假设，一条分支

以后不要在同一条分支里连续叠：

- E 修补
- routing 改造
- selector 改造
- HyperLens
- XB decouple
- B rescue

每个方向单独开分支，单独结束，单独裁决。

### 规则 3：先做减法，再做加法

以后优先问：

- 是哪个最小组件真正有效？
- 去掉哪个模块以后反而更好？
- 最小增益能否稳定复现？

在没回答这些问题前，不再引入新的复合结构。

### 规则 4：没有多 seed，不做主线判断

单 seed 只能说明“值得继续看”，不能说明“值得合并主线”。

主线决策至少需要：

- 统一配置
- 统一结果表
- 至少 3 seed 均值

### 规则 5：结果文件按实验目录裁决，不按总表裁决

以后判断一个实验是否成功，只看：

- 该次实验自己的 `summary.csv`
- 该次实验自己的 `summary_mean.csv`
- 该次实验自己的 `diagnosis.csv`

总表只能做索引，不能做最终裁决依据。

### 规则 6：工程资产和模型资产分开维护

以后要明确区分：

- 模型主线分支
- 实验探索分支
- 自动化/平台分支

不再把三者混在一起推进。

## 对当前仓库的实际操作结论

1. `1a7a137` 之后的模型结构提交，默认全部视为失败假设归档。
2. 后续如果要回看，只把它们当“反例库”和“局部消融参考”。
3. `master2` 从 `1a7a137` 重新开始开发。
4. 后续任何想从旧分支回捞的改动，都必须单独证明是工程改进，且不能改变模型行为；否则不回捞。

## 一句话总结

这段历史最大的教训不是“某个模块没调好”，而是：

在没有稳定打赢基线之前，主线过早地追求结构复杂度、叙事完整度和自动化规模，导致模型越来越难解释、越来越难回退，但效果没有变得更好。

后续开发必须反过来做：

先守住基线，再做最小增益；先做单假设验证，再谈结构升级；先证明 full 值得存在，再决定是否让它进入主线。
