# Codex 写作约束：CD 论文去 AI 味规则

用于后续让 Codex 修改认知诊断论文时作为系统提示或项目说明，不要并入论文正文。

## 总原则

1. 按正常论文逻辑写：问题场景 → 方法模块 → 实验结果 → 讨论边界。
2. 少用自我证明式语言，多用具体任务、模块动作和实验名称。
3. 不要把论文写成内部实验审计或审稿回复。

## 禁用或慎用表达

避免在正文中使用：

- 可审计、审计
- 证据链、操作性机制证据、证据包
- 主证据、弱证据
- 充分必要性证明、不是数学意义证明
- 不能完全排除、不能证明、无法说明
- 顶会论文通常怎么写、本文不应该写成……

## 推荐替换

| 不推荐 | 推荐 |
|---|---|
| 可审计路线图 | 显式概念路线 / 训练日志构造的概念路线图 |
| 机制证据链 | 路线检索、支持集扰动、学习者状态反事实和同题个案分析 |
| 操作性机制证据 | 实验结果 / 分析结果 |
| 弱证据 | 数据集表现存在差异 |
| LCRF 强证 Junyi | Junyi 更接近 CRG-dominant 场景 |
| 不能证明充分必要 | 不写；改成具体结果描述 |

## 摘要写法

摘要只写四件事：

1. 任务背景。
2. 现有方法忽略的具体场景。
3. CRG 和 LCRF 的核心动作。
4. 实验总体结论。

不要在摘要里列过多实验名称、数据集差异或限制说明。

## 引言写法

- 用具体场景说明失败模式。
- Figure 1 只解释问题和直觉，不要堆模块细节。
- 贡献列表只写方法贡献和实验覆盖，不写“验证充分必要”。

## 方法写法

- CRG：从训练日志关系构造全局概念路线图，并给出固定支持集。
- LCRF：在固定支持集内根据学习者状态重排后验路线分布。
- sequence transition 只能写作训练日志中的经验顺序或概念转移，不能写成 prerequisite。
- LCRF 不新增图边、不新增概念，只改变固定支持集内的权重。

## 实验写法

- 表格只放数值，不放“解释”列。
- 有近似值时不要放进表格，可放在图中或正文定性描述。
- 图注描述图中内容和主要趋势，不写“用于证明/用于审计”。
- 结果分析用“表明/显示/说明”，不要写“不能证明/无法排除”。


## 新增主问题实验写作规则

后续补写主问题专项实验时，严格遵守以下边界：

1. **History-to-query route retrieval**
   - 只把 `assist_09` 和 `junyi` 写成正向结果。
   - `assist_17` 在该检索任务上不作为正向结果；后续可用于支持集扰动、覆盖条件预测子组和同题个案。
   - `junyi` 的表述重点是“无题内共现时仍可依赖序列路线”，不要写成所有数据集都成功。

2. **Coverage-conditioned prediction**
   - 只写“收益集中在 direct-unseen-bridgeable、high-route 或 weak-direct 等子场景”。
   - 不要写全体样本上均匀提升。
   - 主文必须补 `n_eval`、Full/no_CRG/no_LCRF 的 AUC 或 BCE、差值和置信区间；没有精确数值时只能写定性 draft。

3. **Direct evidence removal stress test**
   - 不作为主文正向结果。
   - 可放在附录或讨论末尾，用来说明直接概念状态仍是强信号。
   - 推荐表述：CRG-LCRF 是直接覆盖不足时的路线补充，不是直接作答信号的完全替代。

4. **数据集角色**
   - `assist_09`：history-to-query retrieval 与 coverage-conditioned prediction 都可作为主要结果。
   - `junyi`：主要用于无题内共现条件下的数据现象和路线检索。
   - `assist_17`：主要用于支持集扰动、coverage-conditioned prediction 子组和同题个案。

## 讨论写法

讨论只写：

1. 训练路线为什么有用。
2. 固定支持集过滤为什么有用。
3. 数据集表现为什么不同。

不要把讨论写成限制清单。
